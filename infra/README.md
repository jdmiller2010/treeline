# infra: AWS setup for Treeline

Nothing in this directory holds a secret. The secrets live in AWS (SSM Parameter Store) and, for the one credential the VM needs, in a file you install by hand. What may be committed here is in [docs/REPO_RULES.md](../docs/REPO_RULES.md).

> **Status:** `bootstrap/` is tested against a **fake** `aws` (`bootstrap/test_bootstrap.sh`), not a real account. The CDK app is written and its templates are asserted offline (`infra/tests`, a real `cdk synth`), but **nothing has been deployed**: the first real run is the real test, and CloudFormation or Lightsail may reject something the offline checks cannot see. Expect to fix small things, and read what it prints. One thing was already found by running the real AWS CLI rather than assuming: it cannot read a request from stdin (`file:///dev/stdin`), so `bootstrap.sh` writes each request to a private file on tmpfs.

## Before the first deploy: run the bootstrap

Prerequisites on your machine: AWS CLI v2, `jq`, `python3`, `openssl`, and an AWS admin profile that is **not the root user** (`AWS_PROFILE=... aws sso login`). The script refuses root.

```bash
infra/bootstrap/bootstrap.sh check      # what is missing? (read-only; exit 1 if anything is)
infra/bootstrap/bootstrap.sh apply      # create what is missing; asks for the values it cannot make itself
```

It is safe to rerun at any time: it only creates what is missing, and `check` never writes. Rerun `apply` after changing anything below, and `check` before every deploy.

### What it sets up

| Where | What | Where the value comes from |
| --- | --- | --- |
| SSM `/treeline/google_client_id` (String) | Google OAuth client ID (public) | you type it |
| SSM `/treeline/google_client_secret` (SecureString) | the Google OAuth client secret; the app uses it to finish sign-in (authorization code + PKCE) | you type it |
| SSM `/treeline/beta_code_hash` (SecureString), `/treeline/beta_code_expires` (String) | the closed beta's one shared access code, as a SHA-256, and the date it stops working (180 days by default; `TREELINE_BETA_DAYS` changes it). The code lets someone **create a treehouse, once**; grown-ups a parent added sign in with Google alone | generated; **the code is printed once** by `apply` the first time and by `set beta_code` |
| SSM `/treeline/backup_age_recipient` (String) | the age **public** key backups are encrypted to | you run `age-keygen -o treeline-backup.agekey`, keep that file in your password manager, and paste only the `age1...` line |
| SSM `/treeline/admin_cidr` (String) | the only address SSH is allowed from, as `203.0.113.9/32`; `0.0.0.0/0` and anything broader than a /16 are refused | you type it; change it with `set admin_cidr` and run `infra/deploy.sh` |
| SSM `/treeline/alert_email` (SecureString) | where the AWS budget alert goes | you type it |
| SSM `/treeline/healthcheck_url` (SecureString) | the dead-man ping URL: the VM pings it every 5 minutes while the app is healthy and backups are arriving; you are alerted when pings **stop** (which also covers the whole machine being down) | you create a check at a healthchecks-style service (period 5 minutes, grace 15) and paste its https ping URL |
| SSM `/treeline/beta_cidrs` (String) | optional firewall allowlist for 443 and the call audio ports; `none` (the default) means open to everyone. 80 is always open (certificate issuance and the redirect) | `apply` creates it as `none`; `set beta_cidrs` changes it |
| SSM `/treeline/backup_bucket` (String) | the backup bucket's name, with the account id in it, so the VM and the repository never need the id | computed by the script; the CDK stack must create the bucket with exactly this name (a test checks it) |
| SSM `/treeline/vapid_public`, `/treeline/vapid_private` | Web Push key pair | generated by the script |
| SSM `/treeline/smtp_user`, `/treeline/smtp_password` | SES SMTP login | generated: the script makes an IAM user that can only send mail from `@treelinephone.com`, derives the SMTP password from its key, and stores both in SSM. Nothing to copy |
| IAM user `treeline-vm` | what the VM runs as | the script. It may read `/treeline/*`, **write** backups to the bucket `treeline-backups-<account>-<region>` (`central/...` and `households/<id>/...`), and nothing else on the bucket: it cannot read, list, delete or tag objects, or change a lifecycle rule |
| IAM user `treeline-ses-smtp` | sends mail | the script (see above) |
| `infra/.local/vm-credentials` (gitignored, mode 600) | the VM user's access key, until you install it | the script writes it; you install it and delete it |

**Backup retention and purging.** One rule for everything: backups under `central/` and `households/` expire after 7 days (a lifecycle rule in the CDK stack). The VM can only write, so a stolen VM key cannot destroy backups. Shortening a household's call-history retention needs no purge: the live file is trimmed at once and older backups roll off within the week (the app warns about this). **"Delete all my data"**: the app deletes the household's live file and stops backing it up; its backups expire within 7 days. If someone needs backups gone sooner, you delete `households/<id>/` yourself with your admin credentials. The bucket must have versioning **off** (the CDK stack asserts that).

The ARI password is not here: it is generated on the VM at install and never leaves it. The bucket, SES domain identity and DNS records are created later by the CDK stacks, so the policies refer to them by name before they exist; the CDK code must use the same bucket name.

Values are typed at a prompt (or read from `TREELINE_PARAM_<NAME>`, for example `TREELINE_PARAM_GOOGLE_CLIENT_SECRET`) and sent to AWS in a `0600` file on tmpfs that is deleted right after the call, so they never appear in `ps` output, shell history or on disk. A placeholder or malformed value (`<your id>`, an age *private* key as the recipient, a bad email) is refused.

### Getting the key to the VM

Lightsail instances cannot use IAM roles, so the VM holds one access key. After the VM exists:

```bash
infra/bootstrap/bootstrap.sh install-vm-key ubuntu@app.treelinephone.com
```

This copies the key to `/etc/treeline/aws-credentials` (root only, mode 600) and offers to delete the local copy.

### Changing and rotating things

```bash
infra/bootstrap/bootstrap.sh set beta_code          # a NEW access code (shown once); the old one stops working when treeline-api restarts
infra/bootstrap/bootstrap.sh set google_client_id
infra/bootstrap/bootstrap.sh set vapid              # NEW key pair: every parent must turn notifications on again
infra/bootstrap/bootstrap.sh set smtp               # new mail credentials
infra/bootstrap/bootstrap.sh rotate-vm-key          # then install-vm-key, restart, confirm, then:
infra/bootstrap/bootstrap.sh finish-rotate          # delete the old key
```

`check` warns when the VM key is more than 90 days old.

### By hand, if you would rather

The script is plain AWS CLI calls. The equivalent for one parameter (placeholders only). AWS CLI v2 cannot read the request from stdin (`file:///dev/stdin` fails with "Invalid JSON received"), so use a private file on tmpfs and delete it at once:

```bash
f=$(umask 077; mktemp /dev/shm/treeline-param.XXXXXX); trap 'rm -f "$f"' EXIT
printf '%s' '<VALUE>' | jq -R '{Name:"/treeline/google_client_id", Type:"String", Overwrite:false, Tier:"Standard", Value:.}' > "$f"
aws ssm put-parameter --region us-west-2 --cli-input-json "file://$f"
```

## The CDK app

Two stacks (Python, `infra/app.py`; see [docs/DEPLOY_AWS.md](../docs/DEPLOY_AWS.md) work package 6):

- **TreelineFoundation** (retained, termination protection on, everything `RETAIN`): the backup bucket (TLS-only policy, SSE-S3, public access blocked, versioning **off**, 7-day expiry on `central/` and `households/`), the SES identity with DKIM records in your existing hosted zone (imported, never created) plus a `p=none` DMARC record, the 8 GB state disk, and a monthly budget alert.
- **TreelineHost** (replaceable): the Lightsail instance (Ubuntu 24.04, the state disk attached), its static IP, the firewall (22 from `admin_cidr` only, 80 open, 443 and UDP 10000-10100 open or narrowed by `beta_cidrs`; **no IPv6 rule**, so the IPv6 firewall is closed; 5061 closed), and the DNS A records for the app host and the bare domain.

Run this from Linux or WSL (`cdk.json` starts `.venv/bin/python`). SSH is allowed from one address only: if yours changes, run `infra/bootstrap/bootstrap.sh set admin_cidr` (from a place that can still reach AWS) and then `infra/deploy.sh deploy host`; you can also use Lightsail's browser console in the meantime.

One-time setup on your computer (this is the only place `npm` is used, with a pinned CLI and no install scripts; see CLAUDE.md):

```bash
(cd infra && npm ci --ignore-scripts)
python3 -m venv infra/.venv && infra/.venv/bin/pip install --require-hashes --no-deps -r infra/requirements.lock
infra/deploy.sh diff            # then:  infra/deploy.sh deploy
```

`infra/deploy.sh` runs `bootstrap.sh check --quiet` first and **refuses to run `cdk deploy` unless it exits 0**, so a deploy cannot start with a secret missing, a policy that drifted, or no VM key issued. It reads your SSH address, the allowlist, the alert email (from SSM) and the hosted zone id (from Route 53) into **environment variables** for the CDK app: none is written to a file or to this repository, and `cdk.context.json` and `cdk.out/` are gitignored. It also prints the Lightsail bundle (RAM, price) from the real API and stops if the planned bundle (`nano_3_0`) no longer exists. The stacks use the CLI's own credentials (`CliCredentialsStackSynthesizer`), so `cdk bootstrap` is not needed (there are no assets); if CloudFormation asks for it, run it.

`cdk synth` in CI has no AWS account and skips the check; the tests pass dummy settings.

## Tests

```bash
./dev infra        # bootstrap.sh and deploy.sh against the fake aws (in a container that has jq)
infra/.venv/bin/python -m unittest discover -s infra/tests     # the CDK app: template assertions and a real `cdk synth`
```

They use the fake `aws` in `bootstrap/testdata/` and check that rerunning changes nothing, `check` writes nothing, root is refused, bad values are refused, a widened policy is detected and put back, a lost SMTP secret is reissued, the SMTP password matches the documented derivation (checked with an independent HMAC chain), and no secret ever appears in a command line.
