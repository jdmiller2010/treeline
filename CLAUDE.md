# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Treeline: a house-to-house phone network for kids, with parents holding the keys. Each household is a **treehouse** with one line, one 4-digit number, and any number of handsets. Calls connect only over a **string** both families approved. No 911, no outside numbers, no recording. [docs/PLAN.md](docs/PLAN.md) is the phased plan and the source of the decisions; [README.md](README.md) has the status of each phase and the setup. The README says plainly which parts were never run on real hardware or a public server (Phase 4 deploy, Phase 5 adapter, Phase 6 firmware): don't describe them as tested. For the AWS deployment ([docs/DEPLOY_AWS.md](docs/DEPLOY_AWS.md)) the install, the deploy agent, routing, ports, secrets and rollback have run only inside the VM-imitating CI job (`./dev vm`: Ubuntu 24.04 with systemd in Docker, a fake SSM/S3, a local ACME CA); the CDK app has only been synthesized and asserted; on the owner's real VM (no families yet) the install, the upgrade off Ubuntu's Asterisk, an agent deploy with a central migration, HTTPS, Google sign-in and the admin page have run (DEPLOY_AWS.md, "What has run on the real VM"); **never yet**: a call with audio across the internet (NAT), a backup to S3 and its restore, an automatic rollback, SES mail, Lightsail's disk encryption as observed.

## Commands: use `./dev`

`./dev help` lists everything. The usual loop:

```bash
./dev up                 # build + start (only after requirements.txt or a Dockerfile changes)
./dev restart            # after Python changes: the source is mounted into the containers (docker-compose.override.yml)
./dev unit [module]      # unit tests; never touch the dev database
./dev sip [scenario]     # scripted SIP phones (real calls; 22 scenarios)
./dev web [script.py]    # browser softphones on real WebRTC calls (phone_calls.py default, phone_ui.py)
./dev ui smoke           # parent-app browser test on a local API with a throwaway DB (./dev ui start|stop|reset)
./dev ui pwa             # the installable app: manifest, one service worker, the launcher and the install prompts (BROWSER=webkit|msedge|firefox to change engine)
./dev native             # tests for the VM's root-run tools (deploy/native/tests); no root, no Docker
./dev vm                 # the VM-imitating job: install.sh + the deploy agent in a systemd container (~10 min, privileged Docker)
./dev infra              # bootstrap.sh and deploy.sh against a fake aws (in a container with jq); ./dev cdk: the CDK app's assertions
./dev check              # regenerate generated files, syntax-check Python/JS/compose, run the repo rules; fails if something was stale
./dev rules              # scan for secrets, addresses and other things that must not be in this public repo (docs/REPO_RULES.md)
./dev hooks              # once per clone: run those rules on every commit
./dev sbom --table       # the bill of materials: every third-party thing we run, build with or ship
./dev vulns [--os]       # ask OSV.dev about every pinned version (--os: also the VM's Ubuntu packages, needs Docker)
./dev all                # everything
```

On Docker Desktop, host-networked ports aren't reachable from the host, which is why anything needing Asterisk runs in a container and the parent-app test uses its own local API.

## Working rules (each one exists because it went wrong)

- **Use `./dev`, not ad hoc commands.** It holds a lock around anything that uses Asterisk or the dev database (`sip`, `web`, `clean`). If it says another run holds the stack, wait: scenarios, browser softphones and cleanups share one Asterisk, one pjsip file, one `setting` table.
- **Never delete, truncate or `rm` a database a process has open**, and never empty the dev database while a run is in progress. `./dev ui reset` stops the server first; `./dev clean` takes the lock.
- **Never `pkill -f <pattern>` where the pattern appears in your own command** (it kills your shell). `./dev ui stop` uses a pid file.
- **Household files are data too.** `data/households/` holds one file per dev family. Never `rm` one while the api or controller runs (use `households.remove()`, or `./dev clean`, which does and also copes with an old-layout database by stopping the processes first). `./dev ui reset` removes `households/` next to the throwaway database, only while the server is stopped.
- **The dev database may hold a real family** (someone trying the app while tests run). Test queries must be scoped to the test world's own treehouses: "the newest call" or "no calls exist" over the whole database fails when a real softphone dials. (A single dialed digit plus the six-second pause logs a `no_911` call.)
- **Tests force their own resources.** Assign env vars (`os.environ[...] = ...`), never `setdefault`: compose already sets `TREELINE_DB` and the test would hit the real database. Tests that create families in the dev stack must delete them (through the API) when done.
- **Stale code is the most common failure.** Python change: `./dev restart`. Dependency/Dockerfile change: `./dev up`. A "fixed" bug that still reproduces means check which image/process is running before changing more code.
- **Generated files**: after touching `design/ui` icons/illustrations or `THIRD_PARTY_NOTICES.md`, run `./dev check` and commit what it regenerates. A markdown table with a blank line inside it silently breaks the licenses page.
- **Long runs** (scenarios take ~7 minutes): run in the background to a log file and wait with a Monitor; don't poll, and don't start other stack work meanwhile.
- **Test what's real, not what you assume.** Three serious bugs (tones never played, browser phones unable to sign in, a missing DB column) only showed up with real calls, real browsers and an upgraded database. Config for a third-party component (Caddy's certificate path, ARI's comma-split `media`, POST vs PUT to reload a module) must be checked against that component, not recalled. Prefer a test that exercises the audio/registration/upgrade path over one that checks a row.
- **This repo is public: read [docs/REPO_RULES.md](docs/REPO_RULES.md) before committing.** No secrets, no real people (names, emails, addresses, IPs, the places kids play), no account IDs, no database or backup files, no allowlists; placeholders only. `./dev rules` checks it, `./dev hooks` makes git check it on every commit, and CI checks every PR. A finding is never "fixed" by editing history: remove it, and rotate it if it was real.
- **Third-party code**: don't run `npm install` or execute downloaded files. Vendor a pinned download, read it as text, record it in `THIRD_PARTY_NOTICES.md`. **One exception: the AWS CDK command line, scoped to `infra/`** (`package.json` pins `aws-cdk` exactly; `npm ci --ignore-scripts` from the lock file; run from the owner's computer or the CDK CI job, never on the VM or at runtime). Python dependencies for the VM and for `infra/` are installed only from the hash-pinned `*.lock` files (`scripts/make_locks.sh` regenerates them in a throwaway container).
- **Second exception: building Asterisk from source, scoped to `asterisk/build/`.** Only `asterisk/build/build.sh` may run third-party configure and make, only inside the toolchain image pinned by digest in `sources.lock`, started by `asterisk/build/run-build.sh` with `--network none`, on source whose sha256 is in `sources.lock` and whose tarball signature `gpgv` accepted against the committed key. It runs in the `build` and `rebuild` jobs of `.github/workflows/asterisk.yml` and on a developer's machine through `run-build.sh` (and the dev image built from it), and nowhere else: never on the VM, and never in a job that has a write token, `id-token`, an environment or any secret. Only released upstream code is built: no cherry-picked commits, no distribution patches. The bytes a VM installs come only from the published artifact named by its sha256 in `asterisk/build/artifact.lock`, inside the signed release; the release path and the VM job never take Asterisk bytes from a cache or a fresh build. Changing `asterisk-release-key.asc` is a trust-anchor change and needs the owner's review. A change to anything in `asterisk/build/` fails `scripts/asterisk_build.py check` until a new artifact has been built, published and recorded.
- **Every dependency is in the bill of materials, or it is not watched** ([docs/SUPPLY_CHAIN.md](docs/SUPPLY_CHAIN.md)). `scripts/sbom.py` reads the four `*.lock` files, `infra/package-lock.json`, `web/phone/vendor/` (versions from `THIRD_PARTY_NOTICES.md`), the workflows and `install.sh`'s `apt-get install` line; CI asks OSV.dev about each every day. A new lock file, a new vendored file or a new way of installing something must be added to `sbom.py` (and gets a test in `scripts/test_supply_chain.py`). Pin new actions to a commit with a `# vX.Y.Z` comment, GitHub's own actions only. A finding is fixed by updating, or accepted in `.vuln-ignore` with a reason and a date at most 90 days out; never by removing the component from the list. After changing a lock by hand: `python3 scripts/sbom.py --sync-notices`, then `./dev check`.
- **Check the real component, not the fake.** The AWS CLI cannot read `--cli-input-json file:///dev/stdin` (the fake `aws` accepted it for a while); Asterisk refuses its whole pjsip config if an `#include`d file is missing; `ice_host_candidates` is an `rtp.conf` section, not an option. All three were found by running the real thing. A fake that accepts what the real tool rejects is worse than no test.
- **Root-run code never follows a link in a folder another user can write** (the app user's `data/`, Asterisk's folders): use descriptors opened with `O_NOFOLLOW` (`open_data_dir` in `treeline-deploy`, `deploy/native/own-dir.py`), never `install -d -o`, `os.remove` or `shutil` by path (SECURITY.md R6-2, R10-4, R10-5). Test ids for Asterisk builds are `-x<n>`; real builds are `-t<n>` (R10-10).
- **The release is a root-code path.** The deploy agent runs as root and installs what a signature says: never skip or weaken `treeline_release.verify`, never let a release replace `/etc/treeline/release_signers`, and keep the tampered-release tests. `scripts/build_release.sh` takes tracked files only.
- **Playwright**: strings passed to `wait_for_function` are `eval`ed and blocked by our CSP; pass arrow functions (`"(d) => ..."` with `arg=`). Screenshots of full pages show the bottom tab bar mid-page; that's the capture, not a bug.

## Architecture

- **Asterisk never routes on its own.** `asterisk/config/extensions.conf` sends every handset call into `Stasis(treeline)` (ARI). PJSIP accounts for handsets are **generated** from the database into `/generated/pjsip_handsets.conf` by `treeline/pjsip.py`, then Asterisk is told to reload (ARI `PUT /asterisk/modules/res_pjsip.so`; POST *loads*). Asterisk stores only md5 digests (`md5_cred`) of handset secrets. `[global] default_realm` must equal `SIP_REALM` or browser phones can't sign in.
- **`controller/treeline/rules.py`**: `decide()` is the whole call flow, pure logic over the DB (see the README table for the order). Daily minutes, quiet hours (own time zone, per-night days), repeat/hunting limits, busy and offline are all here. Quiet-hours and paused reasons are kept distinct in the audit but sound the same to the caller.
- **`calls.py`** is the ARI call engine: ring every online handset, bridge the first to answer, limit timers with pips, join a call in progress by dialing `0001`, full audit in `call` and `call_event`. It runs on the websocket thread plus timer threads, so it uses `db.local_conn()` (SQLite connections are per-thread). Tones are **named** in `asterisk/config/indications.conf` and played as `tone:<name>`: never put a raw tone string in an ARI `media` list, its commas split the list.
- **`api.py`** (Flask) is everything the apps need: sign-in (Google authorization code + PKCE with a closed-beta access code in production, `google.py`; the emailed six-digit code is the dev and test-suite path only and is a 404 under `TREELINE_ENV=production`), treehouse, strings (string codes, both families approve), handsets, QR/code pairing, adapter settings XML, call log and CSV, push, factory device registration, and it serves the web pages with a CSP. A call involves two families, so what each sees is filtered (`visible_to_callee`, `describe_call`): never leak the other family's quiet hours, rules or unstrung attempts.
- **`db.py` and `households.py`: two kinds of SQLite file** ([docs/DATA_LAYER.md](docs/DATA_LAYER.md) is the source of the rules). The **central** database (`/data/treeline.db` in dev, `/var/lib/treeline/data/treeline.db` on the VM) holds what the app needs to route calls and to find a household from an outside key (treehouses, handsets, strings, grown-ups, sessions) and the call **ledger** (`call`, `call_event`: calls in progress and the last three days, which `rules.decide()` reads; unchanged). Each treehouse has **its own file**, `households/<id>.db`: its call history (`call_log`, a copy per family **written redacted** when the call ends, so a caller's file never says why the callee wouldn't take the call, and `visible_to_callee()` decides whether the callee gets a copy), its notes (`notice`), its audit log (`parent_action`) and `meta` (retention, consent, 911 acknowledgement). Never put a family's own record in central, and never span two files in one transaction (no `ATTACH`): the write order in DATA_LAYER.md ("Writes that touch two files") is what makes a crash harmless, and `households.reconcile()` (startup, hourly) repairs the rest. Open a household only through `households.conn(tid)` (per-thread, checked against the file's inode, so a file deleted by another thread or by the API/controller process is never written through; only `create()` may make a file), and delete it only with `households.remove(tid)`, which also takes the WAL files and pre-migration copies. Both kinds of file are made by `db.prepare()`: `application_id` marks the kind, `user_version` the schema; an unmarked (old-layout) file, one of the wrong kind or one newer than the code is **refused and left untouched**. **Schema changes:** `SCHEMA` is the frozen version-1 baseline: never edit it; add a numbered step to `db.MIGRATIONS` or `households.HOUSEHOLD_MIGRATIONS` (append-only, one transaction per step, `execute` not `executescript`, expand then contract across releases, and a test that builds a file at the *previous* schema, as DATA_LAYER.md rule 6 says). `jobs.py` runs handset check-ins, alert email and push (visiting each household's notes), and the purge (each family's retention trims only its own file).
- **`web/`**: framework-free ES modules. `web/shared/ui.js` builds the design system's exact markup; its `html` tag escapes everything, and button `attrs` must be an **object** when any value comes from data (a string is raw HTML). `web/parent/` is the hash-routed parent app; `web/phone/` is the rotary softphone: an ordinary Treeline page (brand and tagline, the treehouse's name as the `h1` with a `Presence` for what the phone is doing, the berry `RotaryPhone` on a soft glow with the `CardFile` of approved strings beside it (under it, centred, on phones), a "How to dial" `Sheet` of the guide's pictures with `Steps`, and the footer). The phone and card file markup is copied into `web/shared/assets.js` by `build_web_assets.py`, notice included (the phone says it can't call 911 itself); behavior is from `design/ui/js/treeline.js`: we listen to `tl-rotary-hook/pulse/digit` and fill the card file with `TreelineUI.cardfile(el).setContacts()`. Ringing is `setRinging()` (the handset trembles); the line is `setLine()` (green, pulsing orange, blinking red). `SoftphoneDesk` is no longer used by the app. JsSIP does the calls and Web Audio the tones. Vendored libraries are in `web/phone/vendor/` and listed in `THIRD_PARTY_NOTICES.md`.
- **One app, two modes.** A device is a phone when `treeline.phone` is in localStorage, and then `lockedToPhone()` (`web/shared/pwa.js`) sends every dashboard page back to `/phone/` in the installed app *and* in any browser tab (a new tab is no way out). Only the **parent code** ends it: a 4 to 6 digit PIN a parent sets in Settings (`PUT /api/treehouse/parent-code`; salted scrypt in `treehouse.parent_pin_hash`; five wrong tries lock it for 15 minutes, counted in the database), required before any softphone is added (`needs_pin`). On the phone, "For parents" calls `POST /api/phone/leave` (handset Basic auth + the code), which removes the handset; then a signed-in parent goes to `/parent/#/home`, anyone else to the first screen. A forgotten code has a way out that signs nobody in: "I don't know the code" → "Sign out of this browser" (`POST /api/phone/sign-out`, handset auth only) drops the handset, forgets the phone and the parent session, and lands on the first screen, so the dashboard asks for a login. A parent who forgot the code sets a new one right after a fresh sign-in (within 15 minutes) without the old one. Phones and tablets in a browser tab see an install page first (`showInstallPage()`, with a quiet "use it in your browser" link); computers skip it. The profile menu has "Install the app".
- **`deploy/native/`** is production on one Lightsail VM, natively (an upstream Asterisk that each release carries and that we compile from signed source (asterisk/build/README.md), apt Caddy, a venv per release, systemd; **no Docker in production**). `install.sh` is idempotent and refuses a release older than the running one; **all state lives on the attached disk** (databases, Caddy's keys, swap, Asterisk logs), never the system disk. `/var/lib/treeline` is root's: the app user owns only `data/` (the databases) and `spool/`, and root-run tools never write into or follow links in those. Secrets come from SSM into tmpfs at each service start (`treeline-fetch-secrets`); the ARI password is generated on the VM. `TREELINE_ENV=production` (`controller/treeline/prod.py`) makes the API and controller refuse to start with any dev setting (`TREELINE_DEV_CODES`, the default ARI login, `ws://`), and code that came from a release (`release.json` beside it) is production whatever the environment says; the dev sign-in code keeps working for the test suites only because they never set it. Caddy is pinned to one ACME issuer and one storage root; `treeline-certsync` copies its certificate for Asterisk. NAT options for Asterisk (`external_media_address`, `local_net`, the `[ice_host_candidates]` section) are generated at install, never committed. Releases are SSH-signed tarballs (`scripts/build_release.sh`, `.github/workflows/release.yml`); `treeline-deploy` (root) verifies, stages, switches, health-checks and rolls back (restoring the data layer's pre-migration copies when a failed release migrated data), never retries a failed release on its timer, and rebuilds the operator messages on each deploy. Backups are `age`-encrypted on the VM and uploaded write-once (the bucket refuses an overwrite). Google sign-in is bound to the starting browser by a `__Host-` cookie; keep that binding (login CSRF, SECURITY.md R6-1). `deploy/docker-compose.prod.yml` and `deploy/Caddyfile` are the retired Docker plan, kept until the first real deploy.

## UI work

Follow [design/CLAUDE.md](design/CLAUDE.md) and build from `design/ui` (tokens, components, the four page templates, both themes). Every screen sits in the shell or `.tl-root`; one `h1`; at most one primary button; the footer line and the plain "can't call 911" statement where the design requires them. Test at 360, 390, 768, 1024, 1280 and 1440 in both themes. Known kit issue: at narrow widths `.tl-card--breeze`'s extra right padding is overridden, so keep breeze titles short.

## Notes

- Dev passwords and the dev ARI login (`treeline` / `treeline-dev`) are for a private network only. `TREELINE_DEV_CODES=1` returns sign-in codes (to private addresses only): never in production.
- No 911, said plainly: every phone, the softphone and the parent app must state it (see docs/PLAN.md, "Safety and no 911").
- Code is PolyForm Noncommercial 1.0.0 ([LICENSE](LICENSE)); design assets are CC BY-NC 4.0; third-party licenses are in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). Add a dependency there when you add it.
- The code-review findings fixed so far are all covered by tests; keep it that way (a bug found by hand or by review gets a regression test).
- **Security reviews are documented.** After any security review (`/security-review`, an audit of auth, crypto, transport or storage) or security fix, record it in [docs/SECURITY.md](docs/SECURITY.md) following its "How to record a review" section: scope, date, findings (with refs R<n>-<n>), what was clean, what was fixed and the test that covers it, and the open-items table. Never mark something fixed that only was discussed.
