# Security reviews

The record of every security review of Treeline: what was reviewed, when, what was found, and what was done about it. Newest review first. Keep this file current (see "How to record a review" below).

Treeline's security model in one paragraph: in production a grown-up signs in with Google (authorization code with PKCE, bound to the browser that started it; a new family also needs the closed beta's access code once) and holds a 30-day session (stored hashed on the server); the emailed code is the development sign-in only. Handsets authenticate to Asterisk with digest credentials generated from the database. Calls connect only over strings both families approved, and what each family sees of a call is filtered. No recording, no outside numbers, no 911. Production runs natively on one VM with signed releases, secrets from SSM in memory, and age-encrypted write-once backups. See [ARCHITECTURE.md](ARCHITECTURE.md) and [DEPLOY_AWS.md](DEPLOY_AWS.md).

## Review 19: 2026-11-24, the admin step-up against the real Google (branch `stepup-google`; by the change's author, not independent)

**In plain words.** The first real use of the step-up (installing v0.5.0 from the admin page) failed every time, though the owner completed Google's sign-in. Google's own documentation explains why: the step-up asked Google for things Google does not do. It failed closed, so nothing was exposed, but no admin action that needs it could be done. This answers R14-2.

**Finding R19-1 (fixed, Medium for availability, none for confidentiality).** The step-up sent `prompt=login` and `max_age=0` and required a fresh `auth_time` in the ID token. Google supports only `prompt=none`, `consent` and `select_account`; documents no `max_age`; and includes `auth_time` only when asked for through the `claims` parameter and enabled in settings, and then as the original sign-in time (the owner was only asked to choose an account). So `finish()` raised `stepup` on every real attempt (seen twice in the API's journal). The tests passed because their fake Google always put a fresh `auth_time` in the token: the kind of fake CLAUDE.md warns about.

**What the step-up proves now.** A fresh round trip to Google, started by this admin session, finished in the same browser (the binding cookie, R6-1), for the same Google account (`login_hint`, and the token's verified email must equal the session's), with the one-time state and nonce, within the state's ten minutes; it then marks only this session, with a `SameSite=Strict` cookie, for 15 minutes, inside the 12-hour admin session. A copy of the bearer token in another browser cannot do it without the owner's Google account. **Accepted (R19-2, Low):** it no longer proves the password was typed again; someone at the owner's unlocked device, signed in to Google, can pass it. The stronger alternative (a code emailed for each admin action) was offered and not chosen.

**Tests.** The test token is now shaped like Google's (no `auth_time`): `StepUp.test_a_token_like_googles_with_no_auth_time_confirms`; only parameters Google supports are sent: `...test_google_is_asked_with_values_it_supports_for_the_same_account`; a different account, another sign-in's nonce or an unverified email confirm nothing: `...test_what_does_not_prove_it_is_them_now_is_refused`; a replayed answer confirms nothing: `...test_a_confirmation_works_once`; the existing other-browser, stolen-token and cookie tests are unchanged and pass. The refusal is now logged with its detail (fixed strings, no personal data), so the next one says which check failed.

**Not yet seen.** A step-up on the real VM with this change: the owner installs the release that carries it from the terminal, then tries an admin action.

## Review 18: 2026-11-23, a family's string code as a closed-beta pass (branch `settings-invite`; by the change's author, not independent, then read by the `/security-review` recorded in Review 17)

**In plain words.** Until now only the one shared beta code (or being added by a parent) let a new Google account past the beta screen. Now a family's string code does too, so a parent can invite a new family with the same QR code they use to string. This changes who can create an account, so it is recorded here.

**Scope.** `api.auth_beta`, `live_ladder_code`, `request_string`, `string_redeem` and `treehouse_create` in `controller/treeline/api.py`; central step 4 (`db.add_ladder_claim`: `ladder_code.claimed_by`, `claimed_at`); `jobs.forget_unfinished_setups`; `web/parent/js/invite.js`, `signin.js`, `setup.js`, `app.js`. Not reviewed: anything else on the branch (the Settings page and Home buttons, which change no access).

**Method.** Read the code paths above against the existing beta rules (Review 4) and the paused-family rules (Review 16), and wrote tests for each property below. Not run on the real VM or with real Google.

**Result.**
- **R18-1 (accepted by the owner, Low).** Any parent can now let new people in: up to 5 at a time (a family has at most 5 unused codes), each code for one Google account, for 7 days. Families vouch for whoever they invite; every pass traces to the family that made the code. The owner chose this over showing the shared beta code to parents (which would work for anyone, without limit, until it expires).
- **R18-2 (fixed, Low, privacy).** A claim keeps the newcomer's email on the code. As first written it was never removed, so the email of someone who never finished setup stayed in the central database, against the promise that an unfinished setup is forgotten after a day. Now the claim is cleared when the code is used, and claims older than a day by anyone without a treehouse are cleared by `forget_unfinished_setups`. Tests: `StringCodeIsABetaPass.test_the_string_code_lets_them_in_and_setup_sends_the_string_request` (cleared on use), `...test_a_claim_by_someone_who_never_made_a_treehouse_is_forgotten_after_a_day`.
- **R18-3 (fixed, Low, privacy; a note below the `/security-review`'s bar).** A newcomer who claimed more than one family's code kept their address on the unused ones, which stayed unusable, for up to 7 days. Setup now lets go of every other claim of theirs. Test: `StringCodeIsABetaPass.test_other_codes_they_claimed_are_let_go_once_their_treehouse_is_made`.
- **Dropped (harmless).** A claim written just before a pending sign-in expires outlives that sign-in until the daily job clears it.

**Checked and clean.**
- A string code that is wrong, used, expired, or from a family that left or is paused reads exactly like a wrong beta code (same status, code and words): `...test_used_expired_and_paused_family_codes_read_like_a_wrong_code`. The beta screen never names the family.
- One claim per code, and a claimed code is nobody else's pass and can't be redeemed by an existing family; the same person can sign in again with it: `...test_a_claimed_code_is_nobody_elses_pass_or_string_but_the_same_person_can_sign_in_again`. - Setup still makes the treehouse when the string can't be made (the inviter left or was paused) and says why: `...test_setup_still_makes_the_treehouse_when_the_string_cant_be_made`. The other family still approves every string.
- Rule 6 test for central step 4: `LadderClaimMigration.test_step_4_adds_the_claim_and_keeps_the_codes`.


**Remediation taken.** R18-2 and R18-3 fixed on this branch, with the tests above. `/security-review` (Review 17): no findings on this branch.

## How to record a review

Claude: do this every time a security review is run (`/security-review`, a review of auth, crypto, transport or storage, or any audit the owner asks for), and every time a security fix lands.

1. **Add a new "Review N" section** at the top of the reviews, under "Open items". Use the date from the system, not a guess (`date +%F`). Include: **Scope** (what code, which commits or branch, what was and was not read), **Method** (how it was reviewed, and what the review could not see), **Result** (every finding with file and line, severity, and verified confidence, including ones dropped as below threshold), **Checked and clean** (what was looked at and held up), and **Remediation taken** (what changed, in which commit, and what test covers it; "None yet" if nothing).
2. **Give each finding a ref** `R<review>-<n>` and add it to the "Open items" table. When it is fixed, change its status to "Fixed in <commit>" and note the regression test. A security fix without a test is not finished (see CLAUDE.md).
3. **Be honest about limits.** Say what was not reviewed, what was not run, and what only works on a real device or public server. Never record a finding as fixed that was only discussed.
4. **Record dropped findings too**, with the reason, so the next review doesn't redo the work.
5. **Update when fixing later.** A fix in a later session edits the original review's "Remediation" and the open-items row; don't leave the record saying "open".
6. **Commit the doc with the change it describes** (or right after), and keep [README.md](../README.md)'s docs list and the review's `Open items` in step.
